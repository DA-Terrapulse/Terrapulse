\section{PHP Frontend}
\abschnittsautor{D. E. Leuska}

The dashboard represents the frontend of the system. It runs in a browser and presents
sensor readings to the user. The backend runs on a local server and receives
readings from the gateway. PHP can process server requests and return either
complete HTML pages or data for a separate frontend. In this design, HTML and CSS
define the page while JavaScript updates its displayed values \cite{php-syntax-html,gfg-php-introduction}. 
An example can of this is displayed in fig. \ref{abb:example-fig1}.

The frontend communicates with the PHP backend by sending HTTP requests to an
application programming interface (API). The API defines which readings can
be requested and how the response is structured. The dashboard can request
recent readings without accessing the database directly. The server can
receive submitted values through PHP request variables, but it must validate
them before use \cite{php-tutorial-forms,w3schools-php-forms}.

JSON is a suitable format for sensor data because it represents structured
records that JavaScript can read. PHP provides the function \texttt{json\_encode} to
convert server data into JSON. Each response should
identify the sensor, measurement time and units. This consistent format lets
the dashboard display different sensors in the same way \cite{php-json-encode}.

The backend has to handle invalid requests and unavailable data explicitly.
Database values should be passed through prepared statements rather than being
inserted into SQL text. The dashboard should indicate
in case the server cannot be reached or a reading is out of date. Displaying the
measurement time prevents old data from appearing current \cite{php-pdo-prepared}.

\subsection{Polling vs. Interrupt}

Interaction between environment sensors, radio devices and the server is mandatory, which
is why there has to be a mechanism that handles these communications. Two of the most popular 
strategies to solve this case are Polling and Interrupt.

\subsubsection{Polling}

This solution is a protocol that a server can use to question each and every device individually
until one of them needs the servers attention because of any new sensor reading updates. On
one hand, this variant is easy to implement, while on the other hand it consumes more
ressources and is extremely inefficient. How polling works is shown in fig. \ref{abb:example-fig2}.

\subsubsection{Interrupt}
Unlike polling works, interrupt is a mechanism that briefly stops the server at any time when
a new signal arrives. The server quickly turns to an interrupt handler, also known as
interrupt service handlers (ISR) and continues after control is handed over. Although it feels
near-instant, too much task to be handled can make latency noticeable.
