\section{Mesh Devices} 
\subsection{Connectivity Pratices}
\abschnittsautor{J. Tremurici}
The used Meshtastic/Meshcore devices are essentially just radios. This means that the same principles to maximise consistency and range apply. The easiest to implement is the position of the node. It is best to place it as high above the ground as possible, this is usually done by attaching a weatherproof box on a pole to ensure the operability of the device under harsh conditions. The box is for the device itself because the length of the coax cable for the antenna should be kept as short as possible due to signal loss. This height advantage also contributes to a better aerial that isnt as hindered by terrain, foliage, or interference. The biggest factor this could achieve is a direct line of sight (LOS), which is also why nodes are usually kept at high altitude locations like mountains.

A directional antenna can be used for specific circumstances if the location of the nodes allows it. This would allow for communications over much greater distances.

\subsection{Choosing the right Protocol as a Foundation}
\abschnittsautor{J. Tremurici}

This Project matches a lot of the criteria for the LoRaWAN option, although because of the already existing avalaible coverage Meshcore may be preferred. To add, Meshcore works better when the project is designed and built from the ground up where the other is better for a bought solution that a company may contract someone for.

On the other hand, Meshtastic is a lot more popular in developement and area coverage. It is very notable for its low barrier to entry and works better for decentralized applications where not all participants plan the Topology, but rather, only have a client node on them. This is because of its "managed flood" routing protocol, where every device can act as a repeater.

Meshcore is built to be unique in that specific aspect. Every Node in the mesh has a set role and only one of those roles, a repeater, can forward messages. It also stores the path inside the packages so the second successful package will be sent only through a dedicated path and not by flooding the entire mesh. This works far more efficient for a planned Network with always-on, fixed infrastructure nodes. Room Servers can also be used for reliability and integrity of the sent client information. These nodes are dedicated bulletin boards. They handle public group chats and store messages for users who are currently offline.

\section{Dashboard Integration}
\subsection{Concept}
\abschnittsautor{D. E. Leuska}

The planned data flow begins when sensors automatically send measurements
at regular intervals over the radio network to the gateway. The gateway
forwards these measurements to the server, which captures and stores them.
The server then makes the captured readings available to a PHP endpoint.
The browser requests a snapshot of these readings from the endpoint over the
local network. This keeps the dashboard independent from the radio devices
and avoids dependence on an external web service. In \ref{abb:sens-dash-fig}, a visualization 
of the concept can be seen.

\begin{figure}[htbp]
    \centering
    \includegraphics[width=0.75\linewidth]{images/sensor-dashboard_figure.png}
    \caption{Path from sensor to user dashboard}
    \label{abb:sens-dash-fig}
\end{figure}

The endpoint can return recent measurements as JSON. Each record should
contain a sensor identifier, a measurement time and values with clear units.
PHP's \texttt{json\_encode} function can create this response from data read
by the server. The response format should remain the
same for each sensor so the dashboard can display readings consistently \cite{php-json-encode}.

The browser queries the server and uses the returned JSON to update the
dashboard. It can load the latest captured measurements when the page opens or
when the user explicitly refreshes the view. The dashboard should display an error message
in case a request fails and should also display the time of the latest successful reading. It
should never present an old measurement as current.

The PHP endpoint must validate requested sensor identifiers and other input.
If it queries a database, it should use prepared statements to pass values
safely to the database. It should distinguish an
unknown sensor from a sensor that has no recent readings. It should also
return a meaningful error message when the server cannot provide data \cite{php-pdo-prepared}.
